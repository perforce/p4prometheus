== Preface

P4Prometheus integrates Perforce Helix Core Server (`p4d`) with https://prometheus.io/[Prometheus] and related monitoring tools. It collects real-time metrics from `p4d` logs, `p4 monitor`, and related sources, then exposes them for Prometheus collection and Grafana dashboards. The metrics can also drive system alerting.

The `p4prometheus` service continuously parses `p4d` logs and writes Prometheus textfile-collector metrics. Other project components interrogate `p4d` and associated logs for supplementary metrics.

:sectnums:
== Overview

P4Prometheus is part of a monitoring solution comprising these components:

* https://prometheus.io/[Prometheus]: time-series metrics management.
* https://github.com/VictoriaMetrics/VictoriaMetrics[VictoriaMetrics]: recommended, Prometheus-compatible long-term metrics storage.
* https://grafana.com/[Grafana]: metrics dashboards and visualization.
* https://github.com/prometheus/node_exporter[node_exporter]: Linux host metrics and textfile collection.
* https://github.com/prometheus-community/windows_exporter[windows_exporter]: Windows host metrics.
* https://github.com/prometheus/alertmanager[Alertmanager]: alert routing, grouping, and de-duplication.
* https://github.com/rcowham/pint[Pint]: Prometheus alerting rules linter - fork of Cloudflare original.

In addition to these components you can create a monitoring solution tailored to your environment, with automation and alerting including:

* Alerts being sent to Slack (or Teams/Email/PagerDuty)
** Such alerts containing links to relevant Grafana dashboards, and a Runbook for incident response, help ensure timely and effective handling of incidents.
** Options for alerting include notifications of blocked commands, and automated updates when blocks reduce
* Monitoring of Memory usage, and optional OOM-kill events (Out-Of-Memory killer) on Linux hosts.

Project components:

* link:../releases/latest[p4prometheus]: a binary that parses P4 Server logs.
* link:../cmd/p4metrics/README.md[p4metrics]: supplementary P4 Server and SDP-compatible metrics.
* link:../scripts/monitor_locks.py[monitor_locks.py] and link:../scripts/p4monitor_locks.sh[p4monitor_locks.sh]: Linux lock monitoring using `lslocks` and `p4 monitor show`.
* link:../cmd/p4logtail/README.md[p4logtail] and link:../cmd/p4plogtail/README.md[p4plogtail]: completed-command log tails with JSON output (for use with third party log analysis tools such as Splunk, DataDog, ELK Stack etc.)

P4Prometheus uses https://github.com/rcowham/go-libp4dlog[go-libp4dlog] for p4d log parsing.

The installation and upgrade scripts support standard installation, dedicated data volumes (`-d /data`), offline assets (`--local-tarballs-dir`), SDP-safe configuration in `/p4/common/site/config/`, hostname-specific HMS fleet configuration, and stateful non-destructive upgrades. See link:P4Prometheus_Installation.adoc[the installation guide] for details.

=== p4prometheus Metrics

The primary log parser reports command throughput, active commands, resource use, synchronization activity, command error counts, command durations, and lock wait/held time.

[cols="1,2",options="header"]
|===
|Metric family |Examples

|Parser health and throughput
|`p4_prom_log_lines_read`, `p4_prom_cmds_processed`, `p4_prom_cmds_pending`

|Command activity
|`p4_cmd_running`, `p4_cmd_counter`, `p4_cmd_cumulative_seconds`

|Resource use
|`p4_prom_cpu_user`, `p4_prom_cpu_system`, `p4_prom_memory`

|Command dimensions
|`p4_cmd_user_counter`, `p4_cmd_ip_counter`, `p4_cmd_replica_counter`, `p4_cmd_program_counter`

|Command cost (optional)
|`p4_cmd_cost_cumulative`, `p4_cmd_user_cost_cumulative`

|Rate-limit errors
|`p4_cmd_rate_limit_errors`, `p4_cmd_max_cost_errors`

|Lock timings
|`p4_total_read_wait_seconds`, `p4_total_read_held_seconds`, `p4_total_write_wait_seconds`, `p4_total_write_held_seconds`
|===

If you are running p4d 2026.2 or later, command cost metrics are available.
Set `output_cmd_cost_by_cmd` and/or `output_cmd_cost_by_user` to `true` in
the p4prometheus configuration to enable these counters. Both default to
`false`; per-user metrics create a series for each user. The counters sum
positive command costs recorded in the log since the collector started.
Commands without a cost field do not contribute, and the parser cannot
distinguish a missing cost from zero.

The rate-limit counters count logged CostThreshold/MaxCommands refusals and
MaxCost terminations, including retries. `output_rate_limit_errors_by_cmd`
defaults to `true`, enabling per-command breakdowns for both types. Set
`output_rate_limit_errors_by_user` to `true` to enable per-user breakdowns;
it defaults to `false` because it may create many series. If the log cannot
associate an error with a user or command, the
corresponding label is `(unknown)`. Counters reset when the collector restarts.

=== p4metrics Metrics

`p4metrics` replaces the legacy `monitor_metrics.sh` metrics while retaining compatible names and labels. It reports active processes, memory, server identity and uptime, replication, journal/log rotation, license state, SDP job results, Swarm status, and optional memory-limit enforcement.

[cols="1,2",options="header"]
|===
|Metric family |Examples

|Process monitoring
|`p4_monitor_by_cmd`, `p4_monitor_by_prog`, `p4_monitor_by_state`, `p4_monitor_by_user`, `p4_monitor_max_cmd_time`

|Memory and limits
|`p4_active_memory_by_cmd`, `p4_active_memory_by_user`, `p4_memlimit_kill_candidates`, `p4_memlimit_kills_total`

|Replication
|`p4_pull_queue_total`, `p4_pull_replica_lag`, `p4_pull_replication_error`

|Server and license
|`p4_server_uptime`, `p4_p4d_build_info`, `p4_license_expires`, `p4_licensed_user_count`

|SDP jobs and logs
|`p4_sdp_checkpoint_error`, `p4_sdp_verify_errors`, `p4_journal_size`, `p4_log_size`

|Swarm
|`p4_swarm_error`, `p4_swarm_tasks`, `p4_swarm_workers`, `p4_swarm_version`
|===

`p4_monitor_by_prog{prog}` counts monitor-table entries by client program. The
text " (brokered)" is removed from program names. It is enabled by default;
set `cmds_by_prog: false` in the p4metrics configuration to disable it.

=== Lock Metrics

Linux lock monitoring requires `lslocks`. `p4monitor_locks.sh` invokes `monitor_locks.py`, which relates operating-system locks to `p4 monitor show` results. It reports:

* `p4_locks_db_read` and `p4_locks_db_write`
* `p4_locks_cliententity_read` and `p4_locks_cliententity_write`
* `p4_locks_meta_read` and `p4_locks_meta_write`
* `p4_locks_cmds_blocked`

The detailed lock-monitoring installation and troubleshooting information is in link:P4Prometheus_Installation.adoc[P4Prometheus Installation].
