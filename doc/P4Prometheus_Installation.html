Preface

P4Prometheus installation is automated (on Linux) by the scripts in scripts/. Manual component installation is retained in Chapter 5, Manual Installation for environments where automation cannot be used (including Windows).

1. Deployment Roles

Install the following components for each role:

Role Installer and components

Monitoring server

install_prom_graf.sh: Grafana, Prometheus, VictoriaMetrics, node_exporter, and optional Alertmanager, Pushgateway, and Pint.

Helix Core server

install_p4prom.sh: node_exporter, p4prometheus, p4metrics, and lock-monitoring scripts.

Other monitored server

install_node.sh: node_exporter only, for example on Swarm, Hansoft, or Helix TeamHub hosts.

1.1. Expected systemd Services by Role

Use this table to confirm which services should be running (systemctl status <service>) on a given machine after installation:

Role systemd services (installed/enabled by the installer)

Monitoring server

node_exporter, prometheus, victoria-metrics, grafana-server (package-managed), and optionally alertmanager, pushgateway, pint

Helix Core server

node_exporter, p4prometheus, p4metrics, monitor_locks.timer (which runs monitor_locks.service), and optionally vmagent (with -push)

Other monitored server (Swarm, Hansoft, HTH, etc.)

node_exporter only
Only node_exporter runs on "other monitored server" hosts; there is no p4prometheus, p4metrics, or monitoring-stack component to install there.

1.2. Combined-Role Hosts

Some hosts serve more than one role, e.g. a Helix Core replica that also runs Swarm. Do not run install_node.sh on a host where install_p4prom.sh has already been (or will be) run: both scripts install and manage node_exporter, and running both leads to duplicate/conflicting systemd unit definitions.

For a combined Helix Core + Swarm (or other monitored application) host:

  • Run only install_p4prom.sh (it already installs node_exporter).

  • Ensure the node_exporter --collector.textfile.directories value covers metrics written by any other locally-run application (this project only writes p4prometheus/p4metrics .prom files, so metrics from Swarm, etc. would require their own textfile-collector export mechanism configured separately).

  • Run update_p4prom.sh for upgrades on this host; do not additionally run update_node.sh.

2. Automated Installation

Run the relevant installer as root. Download the script from a checkout, or download its raw GitHub URL, make it executable, and review the available options before installing.

p4prom_common.sh is a shared library required by all four install/update scripts (install_prom_graf.sh, update_prom_graf.sh, install_p4prom.sh, update_p4prom.sh). If missing, each script attempts to auto-download it from master on GitHub — but this will fail on a host with no internet access. Always download p4prom_common.sh into the same directory as whichever script you are running, especially for air-gapped installs (see Section 3.3, “Air-Gapped Installation”).

For the monitoring server:

wget https://raw.githubusercontent.com/perforce/p4prometheus/master/scripts/install_prom_graf.sh
wget https://raw.githubusercontent.com/perforce/p4prometheus/master/scripts/p4prom_common.sh
chmod +x install_prom_graf.sh
./install_prom_graf.sh -h

For a Helix Core server, download install_p4prom.sh together with p4prom_common.sh into the same directory:

wget https://raw.githubusercontent.com/perforce/p4prometheus/master/scripts/install_p4prom.sh
wget https://raw.githubusercontent.com/perforce/p4prometheus/master/scripts/p4prom_common.sh
chmod +x install_p4prom.sh
./install_p4prom.sh -h

# SDP instance 1
./install_p4prom.sh 1

For a non-SDP server, use ./install_p4prom.sh -nosdp -h to review the required connection and path options before installing.

2.2. Script Reference

2.2.1. install_prom_graf.sh

This section provides a reference for the install_prom_graf.sh script, including usage and available options.

Usage
   echo "USAGE for install_prom_graf.sh:

    install_prom_graf.sh [-d <data_root>] [-b <bin_dir>] [-r <months>]
                         [-target <host:port>] [-grafana-setup]
                         [--local-tarballs-dir <path>]
                         [-push] [-pint]

or

    install_prom_graf.sh -h

    -d <data_root>          Base directory for all runtime data.
                            Default: /var/lib
                            Example: -d /data  (puts all data under /data/)
    -b <bin_dir>            Directory for installed binaries.
                            Default: /usr/local/bin
    -r <months>             Metrics retention period in months (for use with VictoriaMetrics).
                            Not used by Prometheus itself, which has a short retention setting.
                            Default: 6
    -target <host:port>     Prometheus scrape target. Repeatable.
                            Example: -target myserver:9100 -target otherserver:9100
                            If not specified, a placeholder is written to prometheus.yml.
    -grafana-setup          Create Grafana datasource for Victoria Metrics and
                            import recommended dashboards from INSTALL.md.
    --local-tarballs-dir <p>  Directory containing pre-staged release tarballs.
                            Skips all downloads - for air-gapped environments.
                            Files must match GitHub release asset names exactly.
    -push                   Install Pushgateway (not installed by default).
                            This is generally deprecated in favor of using VMAgent remotely.
    -pint                   Install Pint linter and create pint.service
                            for continuous validation of /etc/prometheus/perforce_rules.yml.

Example:

    sudo ./install_prom_graf.sh -d /data -b /opt/bin -r 12 -target myserver:9100 -grafana-setup
    sudo ./install_prom_graf.sh -grafana-setup
    sudo ./install_prom_graf.sh -d /data -target myp4:9100 -target myreplica:9100 -grafana-setup
    sudo ./install_prom_graf.sh -pint
"

2.2.7. migrate_prom_graf_data.sh

Moves existing monitoring-server data to a different base directory without a full reinstall.

Usage
# Usage:
#   migrate_prom_graf_data.sh -d <new_data_root> [--dry-run] [--cleanup-old]
#
# Flags:
#   -d <new_data_root>   REQUIRED. New base directory (e.g. /data or /hxdata)
#   --dry-run            Show what would be done; make no changes
#   --cleanup-old        After successful migration, remove old data directories
#                        (default: leave originals; safe to re-run)
#   -h, --help           Show this usage text
#
# Preflight checks performed:
#   - New data root is on a writable filesystem
#   - Sufficient free space at destination (current usage + 10% headroom)
#   - All affected services are present (will be stopped/started)
#   - No source/dest overlap
#
# Services stopped for migration (then restarted):
#   prometheus, alertmanager, victoria-metrics, grafana-server, pushgateway
#
# After migration:
#   - /etc/grafana/grafana.ini [paths.data] is updated
#   - Systemd service files are regenerated with new paths
#   - State file is updated with new DATA_ROOT
#   - Old directories are left intact (renamed with .migrated-YYYYMMDD suffix)
#     unless --cleanup-old is passed
#
# Recovery:
#   If this script is interrupted, old data is still in place.  Simply run
#   migrate_prom_graf_data.sh again; it will skip components whose data has
#   already been moved.

2.3. Upgrades

In an SDP environment, run the update checker as the perforce user:

cd /p4/common/site/bin
./check_for_updates.sh
sudo ./update_p4prom.sh 1

For very old installations where update_p4prom.sh was not downloaded, remove .update_config and rerun check_for_updates.sh. Alternatively, download update_p4prom.sh directly, review -h, and run it as root.

3. Enterprise Options

All install and update scripts support a common set of options. Run the appropriate script with -h for the complete list.

3.1. Dedicated Data Volume

Use -d to keep monitoring data on a dedicated volume:

sudo ./install_prom_graf.sh -d /data
sudo ./update_prom_graf.sh
The -d (and -b) path must already exist (e.g. a volume you have deliberately created or mounted) before running the installer. The scripts will fail with an error rather than create missing top-level paths automatically — this avoids silently writing data to the root filesystem if an intended dedicated volume failed to mount.

The selected path is retained in /etc/p4prometheus-monitoring/install.env. To move an existing installation, use:

sudo ./migrate_prom_graf_data.sh -d /data --dry-run
sudo ./migrate_prom_graf_data.sh -d /data
sudo ./migrate_prom_graf_data.sh -d /data --cleanup-old

3.1.1. What -d does and does not relocate

-d relocates the runtime data directories only (Prometheus TSDB, VictoriaMetrics storage, Alertmanager state, Grafana’s data directory, Pushgateway persistence file). It does not move package/config files, which always remain under /etc/ and /usr/share/ regardless of -d:

Path Contents (never relocated by -d)

/etc/grafana/grafana.ini

Grafana’s own config file (it is edited in place to point at the relocated data dir, but the file itself stays here)

/etc/prometheus/prometheus.yml, /etc/prometheus/perforce_rules*.yml

Prometheus configuration and alerting rules

/etc/alertmanager/alertmanager.yml

Alertmanager configuration

/usr/share/grafana/

Grafana application files (package-managed)

/etc/systemd/system/*.service

systemd unit files (fixed location by systemd convention)

3.2. Retention, Binaries, and Targets

# Retain metrics for 12 months and use a custom binary directory.
sudo ./install_prom_graf.sh -d /data -r 12 -b /opt/monitoring/bin

# Add scrape targets during installation.
sudo ./install_prom_graf.sh -target myp4server:9100 -target replica1:9100

3.3. Air-Gapped Installation

Download the required GitHub release assets on a connected machine, transfer them to the target, then pass their directory with --local-tarballs-dir:

sudo ./install_prom_graf.sh -d /data --local-tarballs-dir /opt/installers
sudo ./install_p4prom.sh --local-tarballs-dir /opt/installers

p4prom_common.sh must be pre-staged alongside whichever script you are running on an air-gapped host — this applies to all four scripts (install_prom_graf.sh, update_prom_graf.sh, install_p4prom.sh, update_p4prom.sh), not just the Helix Core server ones. Each script attempts to auto-download it from GitHub if missing, which will fail with no network access.

3.4. Install State and Fleet Configuration

Monitoring-server scripts save state in /etc/p4prometheus-monitoring/install.env. Helix Core server scripts use /p4/common/site/config/p4prom_install.env with SDP, or /etc/p4prometheus/p4prom_install.env without it.

For HMS fleets sharing /p4/common, create a hostname-specific configuration when required:

cp /p4/common/site/config/p4prometheus.yml \
   /p4/common/site/config/p4prometheus.$(hostname -s).yml
systemctl restart p4prometheus

The generated wrappers choose the hostname-specific file before the shared default.

4. Verify Installation

systemctl status p4prometheus p4metrics node_exporter
curl http://localhost:9100/metrics | grep p4_

On the monitoring server, verify Prometheus targets and dashboards after running the relevant installer. See Troubleshooting section next for component-specific checks.

4.1. Troubleshooting

Make sure all firewalls are appropriately configured and the various components on each machine can see each other!

Port defaults are:

  • Monitoring server (the following should be accessible to users)

    • Grafana: 3000

    • Prometheus: 9090

    • Victoria Metrics: 8428

    • Node_exporter: 9100

    • Alertmanager: 9093

  • P4d server(s) - the following should be accessible to the monitoring server to scrape metrics from.

    • Node_exporter: 9100

Use curl on the monitoring server to ensure that you can pull metrics from the other servers (from the target Node Exporter ports) - see below.

4.1.1. On monitoring server

4.1.1.1. prometheus

Access page http://localhost:9090 (or http://<monitoring_server_ip_or_hostname>:9090) in your browser and search for some metrics.

Check the prometheus config file to ensure that it is correctly pointing to the appropriate targets and scrape intervals. The default location is usually /etc/prometheus/prometheus.yml.

Use curl to check targets are accessible, e.g. if yaml contains:

    - targets:
        - p4hms:9100
        - p4main:9100
        - p4_ha:9100

Then:

curl p4hms:9100/metrics | grep p4_
curl p4main:9100/metrics | grep p4_
curl p4_ha:9100/metrics | grep p4_

Problems are most likely due to incorrect target addresses (DNS?), network issues including firewalls, or the node exporter not running on the specified hosts.

4.1.1.2. Victoria Metrics

Access page http://localhost:8428 (or http://<monitoring_server_ip_or_hostname>:8428) in your browser and search for some metrics.

Check the Victoria Metrics config file and the status of the service.

4.1.1.3. Grafana

Check that a suitable data source is setup (i.e. Victoria Metrics or Prometheus) - Section 5.3.1, “Create your first Data Source”

Use the Explore option to look for some basic metrics, e.g. just start typing p4_ and it should autocomplete if it has found p4_ metrics being collected. Alternatively try node_time_seconds

4.1.2. On p4d servers

4.1.2.1. p4prometheus

Make sure the service p4prometheus is running:

sudo systemctl status p4prometheus
sudo journalctl -u p4prometheus --no-pager | tail -20

If this is running correctly, it should write into the designated log file, e.g. /hxlogs/metrics/p4_cmds.prom

You can just grep for the most basic metric a couple of times (make sure it is increasing every minute or so):

$ grep lines /p4/metrics/p4_cmds.prom

# HELP p4_prom_log_lines_read A count of log lines read
# TYPE p4_prom_log_lines_read counter
p4_prom_log_lines_read{serverid="master.1",sdpinst="1"} 7143
4.1.2.2. p4metrics

Make sure the service p4metrics is running:

sudo systemctl status p4metrics
sudo journalctl -u p4metrics --no-pager | less

You can test it via:

p4metrics --config p4metrics.yaml --debug --dry.run

Check that appropriate files are listed in your metrics dir (and are being updated every minute), e.g.

ls -ltr /hxlogs/metrics/
4.1.2.3. node exporter

Make sure node_exporter is working (it is easy for there to be permissions access problems to the metrics dir).

Assuming you have installed the /etc/systemd/system/node_exporter.service then find the ExecStart line and run it manually and check for errors (optionally appending "--log.level=debug").

Check that you can see values:

curl localhost:9100/metrics | grep p4_

If the above is empty, then double check the permissions on `/hxlogs/metrics' or the directory you have configured. Look for errors in:

sudo journalctl -u node_exporter --no-pager | less

5. Manual Installation

The following component-by-component procedures are retained for sites that cannot use the scripts. They are not the recommended default installation path.

5.1. Install Prometheus

This must be done on the monitoring server only. If not using automated scripts then follow these instructions.

Once you have installed prometheus you will need to adjust its configuration file!

Run the following as root:

sudo useradd --no-create-home --shell /bin/false prometheus
sudo mkdir /etc/prometheus
sudo mkdir /var/lib/prometheus
sudo chown prometheus:prometheus /etc/prometheus
sudo chown prometheus:prometheus /var/lib/prometheus

export PVER="2.33.5"
wget https://github.com/prometheus/prometheus/releases/download/v$PVER/prometheus-$PVER.linux-amd64.tar.gz

tar xvf prometheus-$PVER.linux-amd64.tar.gz
mv prometheus-$PVER.linux-amd64 prometheus-files

sudo cp prometheus-files/prometheus /usr/local/bin/
sudo cp prometheus-files/promtool /usr/local/bin/
sudo chown prometheus:prometheus /usr/local/bin/prometheus
sudo chown prometheus:prometheus /usr/local/bin/promtool
sudo chmod 755 /usr/local/bin/prometheus
sudo chmod 755 /usr/local/bin/promtool

sudo cp -r prometheus-files/consoles /etc/prometheus
sudo cp -r prometheus-files/console_libraries /etc/prometheus
sudo chown -R prometheus:prometheus /etc/prometheus/consoles
sudo chown -R prometheus:prometheus /etc/prometheus/console_libraries

Create service file:

cat << EOF > /etc/systemd/system/prometheus.service
[Unit]
Description=Prometheus
Wants=network-online.target
After=network-online.target

[Service]
User=prometheus
Group=prometheus
Type=simple
ExecStart=/usr/local/bin/prometheus \
    --config.file /etc/prometheus/prometheus.yml \
    --storage.tsdb.path /var/lib/prometheus/ \
    --web.console.templates=/etc/prometheus/consoles \
    --web.console.libraries=/etc/prometheus/console_libraries

[Install]
WantedBy=multi-user.target
EOF

5.1.1. Prometheus config

It is important you edit and adjust the targets value appropriately below (see ##### section) to scrape from your commit/edge/replica servers (and localhost).

See later section on enabling Alertmanager if required.

cat << EOF > /etc/prometheus/prometheus.yml
global:
  scrape_interval:     15s # Set the scrape interval to every 15 seconds. Default is every 1 minute.
  evaluation_interval: 15s # Evaluate rules every 15 seconds. The default is every 1 minute.
  # scrape_timeout is set to the global default (10s).

# Alertmanager configuration - optional - uncomment if using
# alerting:
#   alertmanagers:
#   - static_configs:
#     - targets:
#         - localhost:9093

# Load rules once and periodically evaluate them according to the global 'evaluation_interval'.
# Uncomment if using alertmanager
# rule_files:
  # - "perforce_rules.yml"

# A scrape configuration containing exactly one endpoint to scrape:
# Here it's Prometheus itself.
scrape_configs:
  - job_name: 'prometheus'
    static_configs:
    - targets: ['localhost:9090']

  - job_name: 'node_exporter'
    static_configs:

5.4. Install node exporter

This must be done on the Perforce (Helix Core) server machine (ditto for any other servers such as replicas which are being monitored).

Run the following as root:

useradd --no-create-home --shell /bin/false node_exporter

mv node_exporter-$PVER.linux-amd64/node_exporter /usr/local/bin/

If you are installing on a Helix Core commit or replica server, then create a metrics directory, give ownership to account writing metrics, and make sure it has global read access (so node_exporter account can read entries)

mkdir /hxlogs/metrics
chown perforce:perforce /hxlogs/metrics
ls -al /hxlogs/metrics

Ensure the above has global read access (e.g. user perforce will write files, user node_exporter will read them).

If using SDP, then suggest this:

ln -s /hxlogs/metrics /p4/
chown -h perforce:perforce /p4/metrics

Create service file (note value for directory - may need to be adjusted).

Note that when installing on the monitoring machine, you do not need the /hxlogs/metrics directory, and you don’t need the collector.textfile.directory parameter in the service file shown below.

[Unit]
Description=Node Exporter
Wants=network-online.target

[Service]
User=node_exporter
Group=node_exporter
Type=simple
ExecStart=/usr/local/bin/node_exporter --collector.textfile.directory=/hxlogs/metrics

[Install]
WantedBy=multi-user.target
EOF

If using Alertmanager and wanting to check on the status of systemd services, the ExecStart line above should be:

ExecStart=/usr/local/bin/node_exporter --collector.systemd \
        --collector.systemd.unit-include=(p4.*|node_exporter)\.service \
        --collector.textfile.directory=/hxlogs/metrics

# sdp_instance: SDP instance - typically integer, but can be
# See: https://swarm.workshop.perforce.com/projects/perforce-software-sdp for more
# If this value is blank then it is assumed to be a non-SDP instance.
sdp_instance:   1

# ----------------------
# log_path: Path to p4d server log - REQUIRED!
#   Recommended to set an absolute path, e.g. /p4/1/logs/log
log_path:       /p4/1/logs/log

# ----------------------
# metrics_output: Name of output file to write for processing by node_exporter.
# Ensure that node_exporter user has read access to this folder.
metrics_output: /hxlogs/metrics/p4_cmds.prom

# ----------------------
# server_id: Optional - serverid for metrics.
# If SDP install then it will read /p4/<sdp_instance>/root/server.id for
# If non-SDP install, set this field or set server_id_path (this field has preference!)
server_id:

# ----------------------
# server_id_path: Optional - path to server.id file for metrics - only used if non-SDP install.
# If non-SDP install, set either this field, or server_id instead.
# e.g. server_id_path: /opt/perforce/server/root/server.id
server_id_path:

# ----------------------
# output_cmds_by_user: true/false - Whether to output metrics p4_cmd_user_counter/p4_cmd_user_cumulative_seconds
# Normally this should be set to true as the metrics are useful.
# If you have a p4d instance with thousands of users you may find the number
# of metrics labels is too great (one per distinct user), so set this to false.
output_cmds_by_user: true

# ----------------------
# case_sensitive_server: true/false - if output_cmds_by_user=true then if this value is set to false
# all userids will be written in lowercase - otherwise as they occur in the log file
# If not present, this value will default to true on Windows and false otherwise.
case_sensitive_server: true

# ----------------------
# output_cmds_by_ip: true/false - Whether to output metrics p4_cmd_ip_counter/p4_cmd_ip_cumulative_seconds
# Like output_cmds_by_user this can be an issue for larger sites so defaults to false.
output_cmds_by_ip: true

# ----------------------
# output_cmds_by_user_regex: Specifies a Go regex for users for whom to output
# metrics p4_cmd_user_detail_counter (tracks cmd counts per user/per cmd) and
# p4_cmd_user_detail_cumulative_seconds
#
# This can be set to values such as: "" (no users), ".*" (all users), or "swarm|jenkins"
# for just those 2 users. The latter is likely to be appropriate in many sites (keep an eye

output_cmds_by_user_regex: ""

5.6.1. Checking for blocked commands

Look in the log file /p4/1/logs/monitor_metrics.log (or wherever you have configured it to go) for output.

e.g. the following will find all info messages

grep "blocked by pid" /p4/1/logs/monitor_metrics.log | less

Other options to remove client locks (which are output with paths like …​/server.locks/clients/90,d/<client name>):

grep "blocked by pid" /p4/1/logs/monitor_metrics.log | grep -v /clients | less

Output might contain lines like:

2021-06-08 10:42:01 pid 4203, user bldagent, cmd client, table /hxmetadata/p4/1/db1/db.have, blocked by pid 3877, user jim, cmd sync, args c:\Users\jim\p4servers\...#have

It may also be worth checking for commands which are "blocking" others, e.g.

grep blocking /p4/1/logs/monitor_metrics.log

2024-04-04 00:29:02: blocking cmd: elapsed 02:09:23, pid 284460, user perforce, cmd sync, blocking 2, indirectly 203
2024-04-04 00:29:02: blocking cmd: elapsed 00:59:35, pid 374896, user fred, cmd dm-CommitSubmit, blocking 203, indirectly 0
2024-04-04 00:29:02: blocking cmd: elapsed 00:30:45, pid 396091, user fred, cmd shelve, blocking 3, indirectly 0

Please note that metrics (counts of processes locked) are written to /p4/metrics/locks.prom (or your metrics dir) and will be available to Prometheus/Grafana. See P4Prometheus Metrics (look for p4_lock*).

5.7.2.1. Split-file alerting rules (recommended)

update_prom_graf.sh manages two separate rules files to avoid overwriting your customizations on each update:

File Managed by Description

/etc/prometheus/perforce_rules.yml

Script (auto-updated)

Upstream rules from this project. Overwritten when upstream changes.

/etc/prometheus/perforce_rules_local.yml

You

Your site-specific rules. Never touched by the script. Created with helpful comments on first run.

On each update_prom_graf.sh run:

  • If the upstream perforce_rules.yml has changed and you have not modified it locally, it is silently overwritten.

  • If both the upstream has changed and you have local edits, the script backs up your version as perforce_rules.yml.YYYYMMDD before installing the new upstream, then prints a warning reminding you to review and merge any new upstream rules into your perforce_rules_local.yml.

To activate both files, reference them in prometheus.yml:

rule_files:
  - "perforce_rules.yml"
  - "perforce_rules_local.yml"

Then uncomment the relevant section in prometheus.yml:

# Alertmanager configuration - optional
alerting:
  alertmanagers:
  - static_configs:
    - targets:
        - localhost:9093

# Load rules once and periodically evaluate them according to the global 'evaluation_interval'.
rule_files:
  - "perforce_rules.yml"

5.9.1. Windows Exporter

This used to be called "WMI Exporter".

You can download a release, e.g. https://github.com/prometheus-community/windows_exporter/releases

Note that when you run the .MSI file it may appear that it has done nothing - there are no dialogs etc! In fact it will have installed a service called windows_exporter. Look for it with RegEdit.exe under the key HKLM\SYSTEM\CurrentControlSet\Services.

Edit the executable and add the similar parameter to node_exporter: --collector.textfile.directories which must be correctly set and agree with the value used by P4prometheus.

Note that the default port is 9182.

You can test in a similar way to on Linux:

curl http://localhost:9182/metrics

and see what the output is.
